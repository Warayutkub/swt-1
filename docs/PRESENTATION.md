## 0. ก่อนอื่น: pytest หาเทสต์เจอได้ยังไง

**พูดว่า:** ไม่ต้องลงทะเบียนอะไรเลย pytest เดินหาไฟล์เอง

**ทำงานยังไง:**

```
1. อ่าน testpaths จาก pyproject.toml     ->  โฟลเดอร์ tests/
2. หาไฟล์ชื่อ  test_*.py  หรือ  *_test.py
3. ในไฟล์นั้น หาฟังก์ชันชื่อ  test_*  และคลาสชื่อ  Test*
4. เก็บเป็นรายการ "test item" ก่อน แล้วค่อยรันทีหลัง
```

ขั้นที่ 3 กับ 4 แยกกัน เรียกว่า **collection** กับ **execution**
ถึงดูรายการได้โดยไม่ต้องรันจริงด้วย `pytest --collect-only`

**เปิดที่:** `pyproject.toml` → `[tool.pytest.ini_options]`

## 1. `assert`

**พูดว่า:** pytest ไม่มีคำสั่งเทียบค่าของตัวเอง ใช้ `assert` ของภาษา Python ตรง ๆ
แต่เวลาพังมันบอกได้ว่าค่าจริงคืออะไร

**ทำงานยังไง:** เรียกว่า **assertion rewriting**

```
ตอน import ไฟล์เทสต์  pytest ดักไว้ก่อน (import hook)
        ↓
แก้ bytecode ของบรรทัด assert ให้เก็บค่ากลางทางไว้
        ↓
พอพัง จึงพิมพ์ได้ว่า  assert 5000 == 4500
                       where 5000 = calculate_fine(10)
```

ถ้ารัน `assert` ด้วย Python เปล่า ๆ จะได้แค่ `AssertionError` ไม่มีรายละเอียดเลย

**ถ้าโดนถาม** *"ทำไมไม่ใช้ `assertEqual` แบบ unittest"*
→ เพราะไม่ต้องจำชื่อเมธอดเป็นสิบตัว (`assertEqual`, `assertIn`, `assertGreater`...)
ใช้ `==` `in` `>` ของภาษาได้เลย และ pytest แกะให้เหมือนกันหมด

## 2. `pytest.raises`

**พูดว่า:** ยืนยันว่าโค้ด**ต้อง**โยน error ตัวนี้ออกมา ถ้าไม่โยนถือว่าสอบตก

**ทำงานยังไง:** เป็น context manager (`with`)

```
เข้า with   ->  จำไว้ว่ากำลังรอ exception ชนิดไหน
รันโค้ดข้างใน
   ├─ ไม่มี error เลย       ->  เทสต์พัง ("DID NOT RAISE")
   ├─ error คนละชนิด       ->  ปล่อยผ่านไป เทสต์พังตามปกติ
   └─ error ตรงชนิด        ->  จับไว้ เทสต์ผ่าน
```

`match=` เอาข้อความไปหาด้วย `re.search` กับ `str(exception)` — **เป็น regex ไม่ใช่การเทียบตรง ๆ**

`as exc_info` ให้ตัวห่อของ exception กลับมา เข้าถึงของข้างในได้ด้วย `.value`

**เปิดที่:**
- `tests/unit/test_parser.py:83` — ใช้ `match=`
- `tests/unit/test_parser.py:106` — ใช้ `as exc_info` แล้วเช็ค `.line_no`

**ถ้าโดนถาม** *"ทำไมต้องใส่ `match=` ด้วย"*
→ เพราะ `ValueError` ในโปรแกรมมีได้สิบที่ ถ้าไม่เช็คข้อความ เทสต์จะผ่านทั้งที่พังคนละเรื่อง

## 3. `pytest.approx`

**พูดว่า:** เทียบทศนิยมแบบยอมให้คลาดเคลื่อนนิดหน่อย

**ทำงานยังไง:** `approx()` คืน**วัตถุพิเศษที่เขียนทับเครื่องหมาย `==` ของตัวเอง**

```
0.1 + 0.2 == 0.3                   ->  False   (คอมพิวเตอร์เก็บทศนิยมไม่ตรงเป๊ะ)
0.1 + 0.2 == pytest.approx(0.3)    ->  True
```

ค่าเริ่มต้นคือยอมคลาดเคลื่อน 1 ในล้านส่วน ปรับได้ด้วย `rel=` หรือ `abs=`

**เปิดที่:** `tests/unit/test_stats.py:47` — ค่าเฉลี่ยเวลาตอบกลับ 11.75 นาที

**ถ้าโดนถาม** *"ทำไมทศนิยมถึงเทียบตรง ๆ ไม่ได้"*
→ เพราะเลขฐานสองเก็บ 0.1 ได้ไม่ตรงพอดี เหมือนที่เราเขียน 1/3 เป็นทศนิยมให้จบไม่ได้

## 4. `@pytest.fixture`

**พูดว่า:** ของที่เทสต์ต้องใช้ ไม่ต้องสร้างเอง แค่ **"ขอ"** โดยใส่ชื่อเป็นพารามิเตอร์

**ทำงานยังไง:** เรียกว่า **dependency injection**

```
def test_อะไรสักอย่าง(sample_messages):
                       └─────┬─────┘
                             ↓
pytest ส่องชื่อพารามิเตอร์ -> ไปหาในทะเบียน fixture
                          -> เจอ -> เรียกฟังก์ชันนั้น -> เอาค่าที่ได้ยัดใส่ให้
                          -> ไม่เจอ -> error "fixture not found"
```

และ **fixture ขอ fixture ตัวอื่นได้** ทำให้ประกอบกันเป็นชั้น ๆ

```
chat_file  ──ขอ──►  sample_chat_text
    │
    └────ขอ────►  tmp_path (ของ pytest เอง)
```

**เปิดที่:** `tests/conftest.py:53` — `sample_messages` ขอ `sample_chat_text`

**ถ้าโดนถาม** *"ต่างจาก `setUp()` ของ unittest ยังไง"*
→ `setUp` ทำงานเหมือนกันหมดทุกเทสต์ในคลาส ส่วน fixture **เทสต์ไหนขอ อันนั้นถึงทำงาน**
เทสต์ที่ไม่ต้องใช้ฐานข้อมูลก็ไม่ต้องเสียเวลาเปิดฐานข้อมูล

## 5. `yield` ใน fixture

**พูดว่า:** ก่อน `yield` คือการเตรียมของ หลัง `yield` คือการเก็บกวาด

**ทำงานยังไง:** pytest มองฟังก์ชันนี้เป็น generator

```
เรียก fixture  ->  รันจนถึง yield  ->  หยุดค้างไว้ตรงนั้น
                                        ↓
                              ส่งค่าที่ yield ให้เทสต์ใช้
                                        ↓
                              เทสต์รันจนจบ (ผ่านหรือพังก็ตาม)
                                        ↓
                              กลับมารันโค้ดหลัง yield ต่อ
```

**สำคัญ: โค้ดหลัง `yield` ทำงานแม้เทสต์จะพัง** — ของจึงไม่ค้าง ไฟล์ไม่เลอะ

**เปิดที่:** `tests/conftest.py:67` — `workspace` สร้างโฟลเดอร์แล้วลบทิ้ง

## 6. `scope=`

**พูดว่า:** คุมว่า fixture ตัวนี้จะถูกสร้างใหม่บ่อยแค่ไหน

**ทำงานยังไง:** pytest **เก็บผลลัพธ์ไว้ใช้ซ้ำ (cache)** ตามขอบเขตที่กำหนด

| scope | สร้างใหม่เมื่อ | เหมาะกับ |
|---|---|---|
| `function` (ค่าเริ่มต้น) | ทุกเทสต์ | ของที่ต้องสะอาดเสมอ |
| `module` | เปลี่ยนไฟล์ | ของที่แพงปานกลาง |
| `session` | ครั้งเดียวทั้งการรัน | ของที่แพงมาก |

```
scope="function"   ปลอดภัยที่สุด  ช้าที่สุด
scope="session"    เร็วที่สุด      เสี่ยงที่สุด  <- เทสต์แชร์ของชิ้นเดียวกัน
```

**เปิดที่:** `tests/conftest.py:90` — `big_chat_text` แบบ session

**ถ้าโดนถาม** *"ทำไมไม่ใช้ session ให้หมดเลย จะได้เร็ว"*
→ เพราะถ้าเทสต์ตัวหนึ่งแก้ของที่แชร์กัน เทสต์ตัวถัดไปจะพังแบบหาสาเหตุไม่เจอ
และจะพังเฉพาะตอนรันเรียงลำดับนั้น — บั๊กประเภทที่แก้ยากที่สุด

## 8. `@pytest.mark.parametrize`

**พูดว่า:** เขียนเทสต์ครั้งเดียว รันหลายชุดข้อมูล และนับเป็นคนละเทสต์

**ทำงานยังไง:** เกิดขึ้นตอน **collection ไม่ใช่ตอนรัน**

```
ตอนเก็บรายการเทสต์:
   เห็น parametrize ที่มีข้อมูล 6 ชุด
        ↓
   แตกฟังก์ชัน 1 ตัว ออกเป็น test item 6 ตัว
        ↓
   แต่ละตัวมีชื่อของตัวเอง รายงานผลแยกกัน
```

```
test_is_late_night[เที่ยงคืนตรง-เริ่มดึก]     PASSED
test_is_late_night[ตีห้าตรง-หมดช่วงดึก]      FAILED   <- รู้ทันทีว่าเคสไหนพัง
```

ถ้าเขียนเป็น `for` วนในเทสต์ตัวเดียว พอพังจะรู้แค่ว่า "พัง" ไม่รู้ว่าเคสไหน
และเคสที่เหลือจะไม่ถูกรันต่อด้วย

**เปิดที่:** `tests/unit/test_rules.py:28` — เทสต์ขอบเขต "ดึก" 6 เคส

**ถ้าโดนถาม** *"ซ้อนกันสองชั้นได้มั้ย"*
→ ได้ และจะได้ผลคูณกัน — 2 ชั้น × 3 ค่า = 6 เทสต์

## 13. `skip` · `skipif` · `xfail`

**พูดว่า:** สามอย่างนี้ต่างกันชัดเจน อย่าใช้สลับกัน

| | ความหมาย | รันมั้ย |
|---|---|---|
| `skip` | ยังไม่ทำ / อยู่นอกขอบเขต | ❌ ไม่รันเลย |
| `skipif` | รันไม่ได้บนเครื่องนี้ | ❌ ถ้าเงื่อนไขจริง |
| `xfail` | **รู้ว่าพัง** และยังไม่แก้ | ✅ รัน แต่ยอมให้พัง |

**ทำงานยังไง:** `skipif` ถูกประเมิน**ตอน collection** ส่วน `xfail` ต้องรันจริงถึงจะรู้ผล

**`strict=True` คือของดี:**

```
xfail ธรรมดา       พังก็ได้ ผ่านก็ได้              <- เผลอลืมได้ง่าย
xfail(strict=True) ถ้าวันไหนมันผ่าน = เทสต์แดง   <- บังคับให้กลับมาลบ marker
```

**เปิดที่:**
- `tests/unit/test_parser.py:174` — xfail strict (ฟีเจอร์ที่ยังไม่ทำ)
- `tests/unit/test_parser.py:185` — skip (นอกขอบเขต)
- `tests/unit/test_report.py:76` — skipif (ข้ามบน Windows)

## 14. Marker ที่สร้างเอง

**พูดว่า:** ติดป้ายเทสต์ แล้วเลือกรันเฉพาะกลุ่มที่ต้องการ

**ทำงานยังไง:**

```
ในไฟล์เทสต์:   pytestmark = pytest.mark.unit      <- ติดทั้งไฟล์
              @pytest.mark.slow                   <- ติดเฉพาะตัว

ในบรรทัดคำสั่ง: pytest -m unit
               pytest -m "not slow"
               pytest -m "integration and not slow"    <- ใช้ and/or/not ได้
```

marker ที่สร้างเองต้องประกาศใน `pyproject.toml` ก่อน
เพราะเราเปิด `--strict-markers` ไว้ — **พิมพ์ชื่อผิดจะพังทันที ไม่ใช่เงียบ ๆ ข้ามไป**

## 15. Coverage

**พูดว่า:** วัดว่าโค้ดกี่เปอร์เซ็นต์ถูกเทสต์แตะถึง และตั้งเกณฑ์ขั้นต่ำได้

**ทำงานยังไง:**

```
coverage.py เสียบตัวติดตามเข้าไปในตัวแปลภาษา Python
        ↓
ทุกครั้งที่บรรทัดไหนถูกรัน -> ขีดไว้
        ↓
จบการรัน -> เทียบกับบรรทัดทั้งหมด -> ได้เปอร์เซ็นต์
```

เราเปิด `branch = true` ด้วย แปลว่ามันเช็คลึกกว่านั้น:
**`if` ตัวหนึ่งต้องถูกทดสอบทั้งทางจริงและทางเท็จ** ไม่ใช่แค่ผ่านบรรทัดนั้นมา

**เปิดที่:** `pyproject.toml` → `[tool.coverage.report] fail_under = 85`

**ถ้าโดนถาม** *"coverage 100% แปลว่าไม่มีบั๊กใช่มั้ย"*
→ **ไม่ใช่** coverage บอกแค่ว่าบรรทัดนั้นถูก*รัน* ไม่ได้บอกว่าถูก*ตรวจ*
เขียน `calculate_fine(10)` โดยไม่ assert อะไรเลย ก็ได้ coverage เต็ม
เครื่องมือที่ตอบคำถามนี้จริง ๆ คือ **mutation testing** (เช่น `mutmut`) —
มันแก้โค้ดเราให้ผิดแล้วดูว่าเทสต์จับได้มั้ย

# คำถามยากที่น่าจะโดน

### 1. "ทำไม `from .clock import today` แล้ว monkeypatch ไม่ทำงาน"

คำถามนี้โหดและมีโอกาสโดน เพราะมันอยู่ในคอมเมนต์ของโค้ดเรา

```python
from . import clock        # ถูก  -> clock.today() ไปหาค่าตอนเรียกจริง
from .clock import today   # ผิด  -> ผูกตัวฟังก์ชันไว้ตั้งแต่ตอน import
```

แบบที่สอง ชื่อ `today` ในไฟล์เรา**ชี้ไปที่ฟังก์ชันตัวจริงไปแล้ว**
พอ monkeypatch ไปเปลี่ยนของในโมดูล `clock` ชื่อในไฟล์เรายังชี้ที่เดิมอยู่

**เปิดที่:** `src/chatlog/clock.py` — เขียนอธิบายไว้ในเอกสารของโมดูล

### 2. "fixture กับ mock ต่างกันยังไง"

- **fixture** = เตรียมของให้เทสต์ใช้ (ข้อมูล ไฟล์ การเชื่อมต่อ)
- **mock** = แทนของจริงด้วยของปลอม เพื่อไม่ให้ไปแตะโลกภายนอก

ในโปรเจคนี้ `frozen_clock` เป็น **fixture ที่ข้างในทำ mock** — เป็นทั้งสองอย่าง

### 3. "unit กับ integration ต่างกันตรงไหนในงานนี้"

```
unit         ไม่แตะไฟล์ ไม่แตะเน็ต ไม่แตะเวลาจริง    83 เทสต์  0.2 วินาที
integration  ใช้ไฟล์จริงบนดิสก์                      6 เทสต์
```

ดูได้จากของจริง: `pytest -m unit` เทียบกับ `pytest -m integration`

### 4. "ทำไมเทสต์ถึงไม่ยิง API จริง"

ช้า · เสียเงิน · ต้องมีคีย์ · เน็ตล่มแล้วเทสต์แดงทั้งที่โค้ดไม่ผิด · และผลไม่เหมือนเดิมทุกครั้ง
เทสต์ที่ดีต้อง **ให้ผลเดิมเสมอ** ไม่ว่ารันที่ไหนเมื่อไหร่

### 5. "เทสต์เยอะขนาดนี้คุ้มเหรอ"

```
โค้ดระบบ  360 บรรทัด
เทสต์     599 บรรทัด
อัตราส่วน  1.7 : 1      <- งานจริงอยู่ที่ 1:1 ถึง 3:1 เราอยู่ตรงกลาง
```

และเทสต์ทั้งชุดรันจบใน **0.4 วินาที** — ถูกกว่าการเปิดโปรแกรมมากดลองเองทุกครั้งเยอะ

4.  แก้ NIGHT_END เป็น 6:00      รันใหม่ -> แดง 1 เคส ชี้ว่ารู้ทันทีว่าเคสไหน

### ผลจริงของข้อ 4 (วัดมาแล้ว)

แก้ `src/chatlog/rules.py` บรรทัด `NIGHT_END = time(5, 0)` เป็น `time(6, 0)` แล้วรัน:

```
E       assert True is False
E        +  where True = is_late_night(datetime.datetime(2026, 9, 1, 5, 0))

FAILED tests/unit/test_rules.py::test_is_late_night[ตีห้าตรง-หมดช่วงดึก]
1 failed, 5 passed, 86 deselected in 0.13s
```

ชี้ให้ดูสามอย่างในหน้าจอนี้:

1. **พังแค่เคสเดียว** อีก 5 เคสยังเขียว — เพราะ `parametrize` แยกเป็นคนละเทสต์
2. **ชื่อเคสบอกเลยว่าอันไหน** `[ตีห้าตรง-หมดช่วงดึก]` — นี่คือประโยชน์ของ `pytest.param(id=)`
3. **บอกค่าจริงที่ได้** `where True = is_late_night(...)` — นี่คือ assertion rewriting ของข้อ 1

> แก้กลับเป็น `time(5, 0)` แล้วรัน `pytest` อีกครั้ง ต้องได้ `89 passed`
